# Research: 登录接口测试方案

## 1. 空参数 HTTP 状态码决策

**问题**: spec 要求空用户名/空密码返回 400，当前实现返回 401。

**决策**: 保持现有实现返回 401，不在控制器层新增参数校验逻辑。

**理由**:
- 当前 LoginController 将所有非匹配情况统一视为认证失败（401），逻辑简洁一致
- 从安全角度，区分"参数缺失"（400）和"认证失败"（401）会泄露更多实现信息
- 测试的重点是验证认证逻辑的正确性而非参数校验框架

**替代方案**:
- 新增 `@Valid` 注解 + 校验框架 → 过度设计，单接口不需要
- 在控制器中手动 if-null 检查 → 与现有认证逻辑重复，增加分支复杂度

## 2. 技术选型确认

| 维度 | 选择 | 理由 |
|------|------|------|
| 语言版本 | Java 17 | 用户指定，Spring Boot 3.2 原生支持 |
| 测试框架 | JUnit 5 (Jupiter) | Spring Boot Starter Test 默认集成 |
| Mock 框架 | Spring MockMvc | 用户指定，无需启动完整 Servlet 容器 |
| 断言库 | Hamcrest + jsonPath | MockMvc 原生集成 |
| 构建工具 | Maven | 项目已有 pom.xml |
| 覆盖率 | JaCoCo | 项目已配置 |

## 3. 测试范围界定

- **范围内**: LoginController.login() 方法的各类输入输出验证
- **范围外**: 
  - 集成测试（不启动真实服务器）
  - 数据库测试（无数据库依赖）
  - 端到端测试（外部工具压测）
  - DTO 序列化/反序列化（由 Spring 框架保障）

## 4. 高频测试策略

由于 MockMvc 是单线程模拟 HTTP 请求，无法模拟真实并发。高频/压力测试场景需通过"连续快速调用"模拟高频率，验证服务逻辑在快速重复执行下的稳定性。
